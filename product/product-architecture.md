## 0. 一句話定位（研究收斂結論）

> **Yolian = 一個「系統（UI）為主體」的健身工作室營運平台，外加一個 AI Agent 加值窗口 —— 把「教練行政效率」「學員看得見成長」「（選擇性的）跨模組 AI Agent 操作」縫進同一個產品。**
>
> 定位校準：**系統能直接輸入、完成所有事**；Agent 是疊在系統之上的窗口，只在「值得」時介入（口語、語音、跨模組、零碎隨手）。**簡單的事用 Dashboard 解決就好，不必丟給 LLM 浪費 token。**

研究已證實的市場真空（見 deep-dive §5、§6.5）：
- 行政營運（CRM/排課/合約/金流/報表）是紅海，人人都有 → **門檻、非差異化**
- 訓練深度（動作庫/飲食/體態/成長可視化）只有教練類 App 強 → **加分項**
- AI 全市場只到三種：生成內容、唯讀查詢、對外客服賣課 → **沒有人做「教練端、跨模組的對話式寫入操作」**
- **三者同時具備者：0 家** ← 這就是 Yolian 的座標

## 1. 策略與切入點

### 1.1 灘頭堡（Beachhead）
**台灣的個人教練 + 小型工作室（1–10 名教練）** 先行。理由：
- Noki Studio 本身就是這個樣貌（真實用戶 + 共創夥伴）
- OneFloors（NT$490/教練）、青橙「自由教練系統」（19.9 元/月）已驗證「超級個體教練」願付費
- 大型連鎖（17FIT/三体云动/Mindbody 地盤）有金流/門禁/多分店重包袱，不打
- 在地（繁中、台灣金流/發票、LINE 生態）是國際大廠的弱點

### 1.2 三層價值主張
1. **教練**：用講的就完成行政與記錄，少開 Excel/LINE/截圖（對標 SimpleTraining 的效率 + 去掉手動輸入）
2. **學員**：被 AI 用真實數據說出「你的成長故事」，不只看圖表（對標 OneFloors 的成長可視化 + 敘事升級）
3. **AI**：不是功能點，也不是唯一入口，而是**疊在系統之上的加值窗口**——當口語/語音/跨模組比點擊更省事時才用；簡單操作仍走 Dashboard（省 token、體驗更快）

### 1.3 不做什麼（MVP 階段的紀律）
不做大型連鎖的 IoT 門禁、不自建 C 端流量市集（Mindbody/Keep 的護城河無法短期複製）、不一開始就多分店/白標。

## 2. 目標用戶（Personas）

| Persona | 是誰 | 最痛的事 | Yolian 給的解法 |
|---------|------|---------|--------------|
| **獨立教練 Coach Solo** | 自由教練，20–40 名學員，無行政支援 | 排課/記錄/追蹤靠 LINE+Excel+腦袋；課後還要打字記錄 | 一句話排課/記錄/通知；學員成長自動成圖 |
| **工作室主理人 Studio Owner**（= Noki Studio） | 1–10 名教練的小工作室 | 多教練排課衝堂、合約到期沒人追、業績難算 | 多教練排課+衝堂偵測、合約到期提醒、經營儀表板 |
| **學員 Member** | 上私教/團課的會員 | 不知道自己有沒有進步、記錄麻煩、容易放棄 | 拍照/一句話記錄、今日課表、12 週成長敘事 |

> 主決策者/付費者 = 教練與主理人；學員端免費（降低獲客摩擦，對標 OneFloors）。

## 3. 設計原則（決定架構的根本）

1. **Agent 與 UI 共用同一「動作層」**（最重要的架構決策）
   平台所有操作都定義成一組有型別的 **Action（命令）+ Query（查詢）**。程式化前端的每個按鈕，和 Agent 的每句話，**呼叫的是同一套 Action**。→ 點擊與對話永遠一致、不會有「AI 做得到但 UI 做不到」或反之的裂縫；新功能只要新增一個 Action，UI 與 Agent 同時獲得。
2. **Context-aware Agent（經營副駕，而非生成器）**
   Agent 下決策前，能讀到該學員的完整脈絡：訓練數據 + 合約剩餘堂數 + 溝通紀錄 + 續約風險。這是把「生成式 AI」升級成「經營副駕」的關鍵，也是對手（只生成課表、不懂營運）做不到的。
3. **寫入必經確認 + 全程留痕**
   Agent 的每個「寫」動作先回顯「我要做 X，確認嗎？」，執行後寫入 audit log。建立信任、可回溯、可撤銷。
4. **系統（Dashboard）為主體，Agent 為加值、選擇性使用（省 token）**
   系統能直接輸入完成所有操作，Agent 不是必經之路。判準：簡單 / 單一模組 / 批次 / 精細 → 用 Dashboard（快、零 LLM 成本）；口語、語音、跨模組、零碎隨手 → 才用 Agent。**不把容易用點擊解決的事丟給 LLM 浪費 token。** 兩者共用同一 Action 層，隨時可互換。
5. **行動優先、跨平台**（補 OneFloors iOS-only 與 SimpleTraining PWA 的缺）：教練 Web 後台 + 教練/學員行動端。
6. **讓習慣便宜**（借 OneFloors 哲學）：每個高頻動作都壓到「10 秒內、手機上、一兩個點擊或一句話」。
7. **輸入框必須支援語音輸入**：Agent 窗口（教練端與學員端）的輸入框一律支援「語音 → 文字（STT）」。教練帶課中、雙手忙、開車時用講的最自然，這是「讓習慣便宜」的關鍵手段。

│                     │                                       │

│          │   共用 Action / Query 層   │ ← 設計原則 #1        │
│          └──────────────────────────┘                      │
│                     │                                       │
│              核心資料模型 (§5)                              │
│                                                            │
│   面 3：學員端（LINE LIFF）— 今日課表/語音·文字記錄/成長     │
└─────────────────────────────────────────────────────────┘
   原則：簡單的事 → Dashboard（快、零 LLM 成本）
         口語/語音/跨模組 → Agent（值得才用）

- **面 1 程式化前端（主體）**：教練/主理人的 Web + 行動後台。儀表板、行事曆排課、會員清單、合約、訓練課表編輯、報表。**這是系統的主體，多數操作在此直接完成**。對標 SimpleTraining + 17FIT 的完整度。
- **面 2 Agent 窗口（加值層，非必經）**：Yolian 的差異化王牌，但**疊在系統之上**。教練端「一句話 / 一段語音完成跨模組操作 + 主動經營提醒」；**輸入框支援語音輸入**；可常駐側欄或行動端對話框。簡單操作不必走它（省 token）。
- **面 3 學員端**：今日課表、語音/文字記錄、本次 vs 上次、12 週折線、成長敘事、與教練互動交流。跑在 **LINE LIFF（零安裝）**。（拍照記餐辨識為 Phase 2）

## 5. 資訊架構與核心資料模型

### 5.1 核心實體（Entities）

| 實體 | 關鍵欄位 | 關係 |
|------|---------|------|
| **Studio** 工作室/品牌 | 名稱、營業資訊、品牌頁設定 | 1 Studio ─ N Coach |
| **Coach** 教練 | 姓名、角色權限、抽成設定、個人頁 | N Coach ─ N Member |
| **Member** 學員 | 檔案、聯絡、標籤、來源、狀態 | 1 Member ─ N Contract/Booking/Log |
| **Contract** 合約/堂數包 | 方案、總堂數、剩餘堂數、到期日、金額 | 屬於 Member；驅動消課 |
| **Booking** 排課/預約 | 時間、教練、類型(1對1/團課)、狀態、簽到 | 連 Member + Coach；消 Contract 堂數 |
| **Program / Template** 課表/訓練計劃/模板 | 週期類型、分期、含多個 ProgramDay；**模板標籤：目標/程度/焦點/所需器材** | 指派給 Member；可存模板複用、輸出社群內容 |
| **TrainingCycle** 訓練週期/分期 | 微/中週期、週結構(哪天練哪肌群/休息)、漸進策略 | 屬於 Program |
| **ProgramDay** 訓練日 | 焦點肌群、是否休息日、含多個 Block | 屬於 Program/Cycle |
| **Block** 區段 | 類型(熱身/主訓練/伸展/收操)、動作群、組間休息秒數 | 屬於 ProgramDay |
| **Equipment** 器材庫 | 器材名/類型/數量（對應動作 equipment 欄位） | 屬於 Studio；過濾可用動作、驅動器材感知教案 |
| **Exercise** 動作庫 | 名稱、**主/次要肌群**、**類別(肌力/伸展/有氧)**、器材、影片/圖示 | 被 Block/Log 引用 |
| **WorkoutLog** 訓練紀錄 | 每組實際重量/次數、**RIR/RPE**、本次vs上次、完成度 | 屬於 Member + Booking |
| **NutritionLog** 飲食紀錄 | MVP:文字筆記/問答；Phase2:條碼/拍照+四大營養素 | 屬於 Member |
| **BodyComposition** 體組成（客觀數據） | 量測日、**裝置(InBody/Tanita/手動)**、體重、體脂率、體脂肪量、**骨骼肌量(SMM)/肌肉量**、內臟脂肪、體水分、BMR、(選)部位別、報告照 | 屬於 Member；驅動成長折線/敘事 |
| **Order / Payment** 訂單金流 | 品項、金額、狀態、發票 | 連 Contract（Phase 1.5 線上金流） |
| **Payroll** 業績/薪資 | 底薪、售課抽成、完課獎金階梯 | 由 Coach + Booking + Order 算（Phase 1.5） |
| **Message** 溝通 | 對象、內容、自動/手動、已讀 | 連 Member |
| **AgentActionLog** 操作日誌 | 意圖、參數、執行者、前後狀態、可撤銷 | 貫穿所有寫入（設計原則 #3） |
| **Automation** 自動化 | 觸發事件 → 動作鏈 | Phase 2 |

### 5.2 關係重點
- **消課邏輯核心**：Booking 完成簽到 → 扣 Contract 剩餘堂數 → 觸發到期/續約提醒 → 餵給經營副駕算流失風險。這條鏈是「行政」與「AI 副駕」的交會點。
- **成長敘事核心**：WorkoutLog + BodyComposition 隨時間累積 → 學員端折線 + AI 敘事。
- **訓練結構核心**：Program → TrainingCycle（週期/分期）→ ProgramDay（每日焦點肌群/休息日）→ Block（熱身/主訓練/伸展/收操 + 組間休息）；確保肌群平衡、伸展與休息排進循環，而非動作平列。
- **客觀成長核心**：BodyComposition（InBody/Tanita）肌肉量↑、體脂↓ 是「學員看得見成長」最硬的客觀證據。
- 所有寫入都過 Action 層並落 AgentActionLog。

### 5.3 重點功能展開（本次整併）

#### A. 客觀體組成數據（InBody / Tanita）
- **目的**：用儀器客觀數據呈現「肌肉量↑、體脂↓」的變化 = 學員看得見成長的硬證據。
- **支援裝置**：InBody、Tanita（皆 BIA 體組成分析儀）+ 手動輸入。device-agnostic：存共同核心欄位 + 裝置別。
- **共通核心欄位**（兩家對應）：體重、體脂率(PBF)、體脂肪量、骨骼肌量(InBody=SMM)/肌肉量(Tanita)、內臟脂肪(等級/面積)、體水分、基礎代謝(BMR)；選填：部位別(節段)、InBody 分數、BMI、蛋白質/礦物質、代謝年齡(Tanita)。
- **輸入方式**：MVP=手動輸入關鍵幾項；Phase 2=拍 InBody/Tanita 報告單 → OCR 自動入帳（對標 OneFloors「InBody 拍照自動入帳」）；裝置直接匯出/API 視廠商後評估。
- **呈現**：各項隨時間變化折線（**體脂↓ + 骨骼肌↑ 雙線最有感**）、前後對照、餵 AI 成長敘事。
- **MVP**：手動記錄 + 變化折線。

#### B. 系統化訓練結構（肌群 / 熱身 / 伸展 / 休息 / 循環）
> 課表不是一串動作平列，而是有結構的運動循環。
- **動作分類**：每個 Exercise 帶主/次要肌群 + 類別（肌力/伸展/有氧）。資料來源 free-exercise-db 已含 `primary/secondaryMuscles` 與 `category`（含 `stretching`）。
- **訓練日 ProgramDay**：每日焦點肌群（胸三頭 / 背二頭 / 腿…）或休息日；系統可檢查**一週肌群是否平衡**。
- **區段 Block（每日課表內的循環）**：熱身 warmup → 主訓練 main（依肌群）→ 伸展 stretch → 收操 cooldown；每動作可設**組間休息秒數**。
- **休息（兩層）**：① 循環中的休息日（rest day）② 組間休息（set rest）。
- **週期/分期 TrainingCycle**：微週期（一週分項 split：推/拉/腿、上/下肢…）、中週期（數週漸進）。MVP 先支援「週分項 + 區段 + 休息日」；自動漸進加重留 Phase 2（見 oss §4.2）。
- **MVP**：肌群標記 + 訓練日焦點 + 熱身/主/伸展/收操區段 + 休息日 + 組間休息秒數 + 分項範本（推拉腿等）。

#### C. 器材感知的教案/模板系統（含社群內容）
> 教練依工作室實際器材，快速組出有效教案，套用到不同進度與強化重點；而好教案本身常就是社群內容。
- **器材庫 Equipment（屬 Studio）**：工作室登錄擁有的器材（自由重量/史密斯/各式機械/壺鈴/TRX/有氧器材…），對應 free-exercise-db 的 `equipment` 欄位 →「動作 ↔ 器材」可互相反查。
- **器材感知生成**：建課表/挑動作時**只出該工作室有的器材**的動作；缺某器材自動建議**替代動作**（同肌群、用現有器材）。系統為主（依器材＋肌群＋目標篩選），Agent 加值（「用我們工作室的器材做一份增肌初學者 3 天分項」）。
- **模板標籤化**：每個教案模板帶 **目標**(增肌/減脂/體態/肌力/復健)、**程度**(初/中/高)、**焦點**(肌群/弱點)、**所需器材組** → 快速搜尋與套用。
- **套用到不同進度**：同一模板產生**進度變體**（初→中→高：加量/加組/換進階動作），或依學員當前數據微調。
- **針對需強化處**：依弱點肌群/目標（可參考體組成節段或教練判斷）挑強化模板。
- **教案即社群內容**：模板可一鍵輸出成**可分享內容卡**（課表卡 Flex Message / 圖文），發到教練品牌頁、LINE（`shareTargetPicker`）、社群 → 行銷與社群經營（連動 §6、§9）。
- **MVP**：器材庫 + 器材感知挑動作/替代 + 模板標籤(目標/程度/焦點)快速套用。進度變體自動化、教案社群內容輸出 → Phase 1.5/2。

## 6. Agent 能力目錄（Yolian 的王牌）

> 設計成「意圖（intent）→ 對應一個或多個 Action/Query」。下表是能力清單，標注讀/寫、涉及模組、是否 MVP。MVP 先做**高頻、低風險、跨模組價值高**的。

### 6.1 教練端 — 操作型（寫）
| 意圖 | 範例自然語言 | 涉及模組 | MVP |
|------|------------|---------|:--:|
| 排課 | 「幫王小明這週三、五早上各排一堂私教」 | Booking | ✅ |
| 改課表 | 「把小明的深蹲加 5 公斤、臥推改 4 組」 | Program | ✅ |
| 記錄完課 | 「小明今天深蹲 100x5 做完了，狀況不錯」 | WorkoutLog + Booking 簽到 | ✅ |
| 通知學員 | 「提醒明天 7 點的學員帶毛巾」 | Message | ✅ |
| 改/取消預約 | 「小明這週四的課改到五早上九點」 | Booking | ✅ |
| 新增學員 | 「新增學員陳小美，電話 09xx，買 10 堂私教」 | Member + Contract | ✅ |
| 指派課表 | 「把『增肌入門 8 週』指派給小美」 | Program/Template | ✅ |
| 記錄體組成 | 「幫小明記今天 InBody：體重 70、體脂 18%、骨骼肌 33」 | BodyComposition | ✅ |
| 依器材生成教案 | 「用我們工作室的器材，做一份增肌初學者 3 天分項課表」 | Program+Equipment | ◐ 部分 |

### 6.2 教練端 — 查詢型（讀）
| 意圖 | 範例自然語言 | 涉及模組 | MVP |
|------|------------|---------|:--:|
| 查堂數 | 「小明還剩幾堂？合約什麼時候到期？」 | Contract | ✅ |
| 查進度 | 「小明這個月深蹲進步多少？」 | WorkoutLog | ✅ |
| 查行程 | 「我明天有幾堂課？」 | Booking | ✅ |
| 查營收 | 「這個月營收多少？比上月如何？」 | Order/Report | ◐ Phase1.5 |

### 6.6 Agent 運作機制（架構）
- **輸入**：文字或**語音輸入（STT 語音轉文字）**；輸入框一律支援語音
- **省 token 路由**：明確、簡單、單一模組的請求可走規則/捷徑或直接導去 Dashboard，不必每次都呼叫 LLM
- **意圖解析**：LLM 將自然語言 → 結構化意圖 + 參數（哪位學員、哪堂課、加多少重量）
- **Tool calling**：意圖對應到 §3.1 共用 Action/Query（function calling）
- **歧義澄清**：缺參數或多個「小明」→ 反問確認
- **寫入確認**：回顯「我要把小明本週三、五 07:00 各排一堂，確認？」→ 執行 → 落 AgentActionLog（可撤銷）
- **脈絡組裝**：執行前載入該 Member 的結構化脈絡（堂數/近況/溝通）→ 餵 LLM 做 context-aware 判斷

## 8. 技術架構建議

### 8.1 核心原則：API-first + 共用 Action 層
- 所有操作 = 後端一組**型別化 Command / Query**（單一事實來源）
- 程式化前端（按鈕）與 Agent（function calling）都呼叫同一套 → 一致、好維護、好擴充
- 每個 Command 自帶權限檢查 + 寫 AgentActionLog

### 8.2 平台（跨平台，補對手缺口）
- **教練後台**：Web（先 PWA 快速上線，對標 SimpleTraining 的 PWA 策略）+ 行動可用
- **學員端**：行動優先（PWA 起步，Phase 2 視需求轉原生以支援拍照辨識體驗）
- 目標：iOS + Android + Web 全覆蓋（OneFloors 僅 iOS、SimpleTraining 純 PWA 都是缺口）

### 8.3 AI Stack
- **LLM + tool calling**：意圖解析 + 呼叫 Action（MVP 即可，繁中能力要好）
- **STT 語音轉文字**：支援語音輸入（輸入框必備）；行動端可用原生 STT 或 Web Speech API，繁中辨識品質要顧
- **省 token 設計**：系統 UI 處理多數操作；只有值得的請求才進 LLM；簡單意圖走規則/快捷；脈絡按需組裝，避免每次塞爆 prompt
- **脈絡組裝**：以結構化資料為主（堂數/紀錄/訊息），輔以 RAG（教練筆記等非結構化）
- **Phase 2 視覺模型**：飲食整盤辨識（對標 OneFloors，成本與準確率需評估，故延後）
- **護欄**：寫入確認、audit log、可撤銷、權限邊界

### 8.4 在地整合（台灣）
LINE（通知/預約入口）、台灣金流與電子發票（Phase 1.5）、繁中 LLM。

## 9. LINE 官方帳號 + LIFF 整合策略（台灣關鍵渠道）★ 補件

> 這是先前藍圖漏掉、但對台灣灘頭堡至關重要的一塊。台灣 LINE 有 **約 2,100 萬活躍用戶**，且研究中幾乎每個台灣競品都靠 LINE（17FIT、BookFast、VibeAI、Trainge、艾美力 imary、SimplyBook.me 全在做 LINE 預約）。LINE 官方主打的場景就是美業/醫療的「**線上預約 + 提醒、降低失約率**」——剛好命中教練痛點。對 Yolian 而言，LINE 不只是通知管道，而是**學員端零安裝的主要交付載體**，直接補掉 OneFloors「僅 iOS」與 SimpleTraining「純 PWA」的缺口。

### 9.1 三個積木（角色分工）
| 積木 | 是什麼 | 對 Yolian 的角色 |
|------|--------|--------------|
| **LINE 官方帳號 (OA)** | 品牌在 LINE 的帳號；含圖文選單、群發/分眾、集點、優惠券、AI 自動回應、聊天 | 工作室/教練的 LINE 門面 + 學員入口 + 推播管道 |
| **Messaging API** | 後端 ↔ LINE 的程式介面（webhook 收訊息、push/reply 發訊息、Flex 卡片、Rich Menu） | 把 LINE 接進 Yolian 的 Action 層：推播提醒 + Agent 對話 |
| **LIFF（LINE Front-end Framework）** | 在 LINE 內建瀏覽器跑的 web app，**零安裝**、可直接取得 LINE 使用者身分 | **學員端主介面**（今日課表/記錄/成長）就跑在 LINE 裡 |

### 9.2 LIFF 能力（已查證，對應 Yolian 用途）
- **零安裝 + 自動身分**：在 LIFF browser 內免登入即可拿到使用者 → `liff.getProfile()` 得 `userId / displayName / pictureUrl`；`liff.getIDToken()/getAccessToken()` 傳後端做帳號連結（LINE userId ⇄ Yolian Member）。
- **三種視窗尺寸**：Compact / Tall / Full（成長頁用 Full、快速記錄用 Tall）。
- **`liff.sendMessages()`**：代使用者在當前聊天送訊息（例如記錄完成回拋一張卡）。
- **`liff.shareTargetPicker()`**：分享給 LINE 好友 → **學員轉介獲客**。
- **`liff.scanCodeV2()`**：掃 QR → **到場簽到/消課**（對標 SimpleTraining 的 QR 簽到）。
- 需求：一個 LINE Login channel + HTTPS endpoint（Yolian 的 web app 直接當 LIFF app 載入，沿用同一套 Action 層）。access token 效期 12 小時。

### 9.3 Messaging API 能力（已查證）
- **收**：使用者傳訊 → webhook 事件（message / follow 加好友 / postback 按鈕 / beacon…）→ 進 Yolian Agent。
- **發**：reply（回覆，**免費**）、push/multicast/broadcast（主動推播，**計費**）。
- **訊息型態**：文字、圖片、**Flex Message（自訂卡片，做課表卡/成長卡）**、Template、Quick Reply、貼圖、位置。
- **Rich Menu（圖文選單）**：聊天室永久置底入口，可放「今日課表 / 我的進度 / 預約 / 聯絡教練」直開 LIFF。
- 其他：account link（安全綁定 Yolian 帳號）、get profile、beacon。

### 9.4 對接 Yolian 三面 + Agent
```
LINE 官方帳號（學員加好友）
   │
   ├── Rich Menu（永久入口）
   │      └─▶ LIFF App = Yolian 學員端（面 3）  零安裝、自動 LINE 身分
   │             今日課表 / 語音·文字記錄 / 本次vs上次 / 12週折線 / 成長敘事
   │
   ├── 使用者傳訊 ──webhook──▶ Yolian Agent（面 2）──reply(免費)──▶ 回覆
   │      「幫我約這週的課」「我這個月進步多少」→ 走同一套 Action/Query 層
   │
   └── push（計費，高價值才用）
          上課提醒(降爽約) / 合約到期 / 週成長摘要 / AI 成長敘事
```
- **學員端（面 3）= LIFF**：這是最大槓桿——學員不必下載任何 App，在 LINE 裡就能用 Yolian，身分自動帶入。**直接解掉 OneFloors iOS-only 的痛**。
- **Agent（面 2）可長在 LINE 對話**：學員/教練在 LINE 打字 → webhook → Yolian Agent → 回覆。等於 Agent 多了一個「人人都在用的入口」。
- **設計原則 #1 延伸**：LIFF 與 webhook 都只是 Action 層的另一個前端，與 Web 後台共用同一套操作，零裂縫。

### 9.5 高價值用例（對應教練/學員痛點）
1. **降低爽約**（LINE 官方招牌場景）：課前 push 提醒 + 一鍵確認/改期 → 直接對應教練營收。
2. **零安裝學員端**：加好友即用，移除「下載 App」這個最大流失點。
3. **QR 簽到消課**：`scanCodeV2` 到場掃碼 → 扣堂數 → 觸發續約提醒鏈。
4. **成長敘事 push**：每週/每季把數據變成一段話推到學員 LINE（留存王牌）。
5. **轉介獲客**：`shareTargetPicker` 學員把教練頁/成果分享給 LINE 好友。
6. **Agent over LINE**：教練零碎指令（「明天 7 點那堂改到九點」）直接在 LINE 講。

### 9.6 成本與限制（務實）
- **計費模型**：reply（回覆使用者）+ 一對一聊天 + 自動回應 + 歡迎訊息 + LINE VOOM **皆不計費**；**群發/分眾/API push 才計費**（按目標好友數×次數）。→ 架構上：**Agent 對話走 reply（免費）、提醒才用 push（精省）**。
- **TW 方案**（2023 改版，**數字以官網計算機為準**）：輕用量（免費，少量訊息）/ 中用量（月費約 NT$800）/ 高用量（月費約 NT$1,200），各含免費訊息額度 + 超量加購。
- **帳號類型**：一般 / 認證(藍盾) / 企業(綠盾)；Messaging API 一般帳號即可用，認證帳號可投「加好友廣告」。2026/4 起一般帳號不再顯示灰盾。
- **健康/醫療業種限制**：LINE 對醫療/金融等敏感業種的「**LINE 內建 AI 聊天機器人(β)**」可能拒絕提供。Yolian 用**自有 Agent（走 Messaging API webhook）不受此限**，但健身鄰近健康，內容合規仍要留意。
- LIFF 限制：需 HTTPS、在 OpenChat 不支援、外部瀏覽器無法用 `scanCode`。

### 9.7 對 MVP 的建議
- **MVP 就把 LINE 當學員端主要交付**：LINE Login 綁定身分 + LIFF 學員端（今日課表/記錄/成長）+ Rich Menu + 上課提醒/合約到期 push。CP 值極高、又是在地剛需。
- **Agent over LINE 對話**：快速跟進（MVP 末或 Phase 1.5），先做學員查詢/預約等 reply（免費）情境。
- 教練端仍以 Web 後台為主（複雜操作），LINE 作為教練零碎指令的補充入口。

### 9.8 競品 LINE 使用對照（佐證這是剛需）
| 競品 | LINE 用法 | 深度 |
|------|----------|------|
| 17FIT | 全通路預約含 LINE、LINE 外掛模組 | 預約/通知 |
| BookFast | 品牌 App + LINE 預約、LINE Pay、自動通知 | 預約/金流/通知 |
| VibeAI | 免費 LINE 預約系統、LINE OAuth、自動提醒降爽約 | 預約/提醒 |
| 艾美力 imary | 主打 LINE 深度整合、私域流量、拒平台抽成 | 私域經營 |
| SimplyBook.me | LINE 預約機器人 | 預約 |
> 結論：台灣「LINE 預約」已是標配，但**沒人把 LINE 當「訓練深度 + 成長敘事 + Agent」的零安裝載體**。Yolian 用 LIFF 把差異化體驗直接送進 LINE，而非只做預約。

## 11. 風險與待決策（請你校準）

**待你決策的關鍵分岔**：
1. ✅ **已定案 — MVP 客群**：直接含「小工作室多教練」（MVP 即含多教練排課協作 + 主理人/教練角色權限）。
2. ✅ **已定案 — 金流**：不進 MVP，採教練自行對帳（手動標記收款）；線上金流延後 Phase 1.5。
3. **飲食拍照辨識**：是否視為核心賣點而提前到 MVP？（技術成本高，但這是 OneFloors 最吸睛功能）
4. **Agent 範圍**：MVP 的 Agent 先做「教練端操作 + 查詢」，學員端對話延後 Phase 2，可接受？
5. **平台順序**：先 Web 後台還是先學員行動端？（建議先 Web 後台 + 學員 PWA）
6. **建置資源**：團隊/時程/預算規模為何？（直接影響 MVP 該砍多少）
7. **LINE 優先級**：是否同意把「LINE LIFF 學員端 + 上課提醒」放進 MVP（我的建議：是，台灣剛需、CP 值最高）？教練端是否也要 LINE 入口，或先純 Web？

**主要風險**：
- Agent 寫入錯誤的信任問題 → 用確認 + 留痕 + 可撤銷緩解
- 動作庫/訓練深度需要量的累積（MoHot/Trainerize 的門檻）→ MVP 可先小庫 + 教練自建
- 繁中 LLM 意圖解析準確率 → 需早期實測
- 與 OneFloors 正面競爭（最像）→ 靠「跨模組 Agent + 完整營運 + 跨平台」拉開
