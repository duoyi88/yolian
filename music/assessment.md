# Yolian Music 適配評估 — 同一商業模式能不能搬到音樂教學？

> 專案：Yolian Music（有練 · 音樂版）— 面向音樂老師與音樂教室的對話式營運平台
> 本文回答一個問題：把 Yolian（健身版）的商業模式，搬到「鋼琴／小提琴等樂器教學」這個相鄰群體，**成不成立、哪裡一樣、哪裡不一樣**。
> 日期：2026-06-25 · 狀態：評估（先決定要不要做、怎麼做；系統細節見 `product-architecture.md`）

---

## 0. 一頁結論（先講判斷）

> **判斷：值得做，但必須是「共用作業系統、抽換訓練引擎、加一層家長」的獨立產品，不是把健身版改個皮。**

- **商業模式：高度可移植（~80%）。** 付費者邏輯、營運痛點、台灣 LINE 渠道、AI 副駕價值、留存引擎，幾乎 1:1 對得上。**通用教練 OS（CRM／排課／合約堂數／簽到消課／訊息／品牌頁／多師權限）可直接沿用**——這正是健身版「OS 與專項內容解耦」鐵律的紅利。
- **三個「不小的差異」（差異）：**
  1. **操作者錯位** — 健身的使用者就是學員本人；音樂的學員多是**小朋友，無法自行操作**。**真正的學員端使用者是家長**。這是最根本的結構差異，牽動帳號模型、通知對象、付費者、練習紀錄、激勵迴路。
  2. **進步引擎完全不同** — 健身引擎是「可量化的負荷漸進（組×次×重量）」；音樂的進步是「**曲目精熟 + 技巧 + 檢定級數**」，靠的是技術/段位軸。在健身版的相容性分級裡，這種「技術/段位」進步**被歸為 T3、明確排除**。→ 音樂**不能套健身引擎，必須自建一套音樂原生引擎**。
  3. **主戰場在「課與課之間」** — 健身的價值發生在「付費課堂」，課外活動是次要（Tier B）。音樂 90% 的進步發生在**每週課之間的家庭練習**，而「小孩不練、家長盯、老師看不到」正是音樂教學的第一痛點。→ 健身版裡次要的「練習追蹤」，在音樂版是**主角**。Tier A／B 重要性翻轉。
- **品牌彩蛋**：「**有練**」在音樂語境**更貼**——每個琴童家長每天問的就是「**今天有練琴嗎？**」。`練` 字本身就是「練琴／練習」。slogan「有練，有差」原封不動成立。
- **做法**：**獨立部署、獨立網頁、獨立品牌敘事**（如你所要求），底層共用 Action 層與 OS 模組，替換訓練引擎 + 疊一層家長帳號。

## 1. 同構假設：為什麼直覺上會通

健身與音樂的「**個人指導服務業**」骨架幾乎一樣：

- 一位專業者（教練／老師）長期、週期性地，**為個別對象持續編排內容**並追蹤成效。
- 收費方式相同：**堂數包 / 月費**，按堂消耗。
- 交付頻率相同：**固定時段的週課**（音樂甚至更固定——「每週三下午 4 點」幾乎是鐵律）。
- 同樣有「**請假／補課**」「**合約到期續約**」「**會不會半途放棄**」的營運難題。
- 台灣同樣都**靠 LINE + 紙本 + 腦袋**在運作，數位化程度低、在地工具缺。

→ 凡是「教練 OS」解的那一層（誰、什麼時候、上了沒、還剩幾堂、收錢了沒、家長怎麼聯絡），**健身與音樂是同一個問題**。這部分可移植性接近滿分。

## 2. 商業模式可移植性（逐層對照）

| 層面 | 健身版 Yolian | 音樂版 Yolian Music | 可移植度 |
|------|--------------|--------------------|:--:|
| **付費者** | 教練／主理人付費，學員免費 | 老師／教室主理人付費，**家長/學生免費** | ★★★ 相同 |
| **灘頭堡** | 台灣個人教練 + 小型工作室(1–10) | 台灣個人音樂老師 + 小型音樂教室/琴行 | ★★★ 同構 |
| **核心痛點** | 排課/記錄/追蹤靠 LINE+Excel+腦袋 | 一模一樣，外加「練習看不到」更痛 | ★★★ 相同+ |
| **CRM / 排課 / 合約堂數 / 簽到消課** | 通用 OS 模組 | **直接沿用** | ★★★ 1:1 |
| **多師協作 + 主理人/老師權限** | MVP 即含 | **直接沿用**（琴行多老師） | ★★★ 1:1 |
| **LINE LIFF 零安裝交付** | 學員端主介面 | **家長端**主介面（價值更高，見 §3.1） | ★★★ 相同+ |
| **AI 副駕（語音記錄 + 經營提醒）** | 教練課後口述記錄 | 老師課後口述「上課摘要 + 回家作業」 | ★★★ 場景更剛需 |
| **留存王牌：成長敘事** | InBody 數據折線 + 故事 | **錄音/錄影對比 + 檢定成果**（見 §3） | ★★☆ 換證據、迴路相同 |
| **品牌頁自動生成** | 教練個人頁 | 老師/教室個人頁 | ★★★ 1:1 |
| **訓練/內容引擎** | 負荷漸進引擎 | **曲目精熟引擎（須重做）** | ☆ 必須抽換 |
| **學員端使用者模型** | 學員本人 | **家長代理層（須新增）** | ☆ 必須新增 |

> 收斂：**綠燈一片，只有最後兩列是紅燈**——而這兩列正是「不小的差異」，也是必須做成獨立產品（而非健身版加個選項）的理由。

## 3. 三個結構性差異（這就是「不小的差異」）

### 3.1 操作者錯位：必須新增「家長代理層」★ 最根本

健身版的隱含假設是「**學員 = App 使用者 = 被通知者 = 行為人**」，四位一體。音樂版這個假設**整個垮掉**：

- 學生多為 **5–15 歲兒童**，沒有手機、不會（也不該）自己操作系統、無法自己收提醒、不付錢。
- **真正的學員端使用者是家長。** 家長才是：收上課提醒的人、看進度的人、付錢續約的人、（盯/陪）練習的人、決定要不要繼續學的人。

**牽動的設計變更：**

| 構面 | 健身版 | 音樂版 |
|------|--------|--------|
| 帳號模型 | 1 學員 = 1 帳號 | **1 家長帳號 ─ N 子女**（一個家長可能有兩個小孩都在學） |
| 學員端身分 | 學員本人 LINE | **家長 LINE**（LIFF 自動帶家長身分） |
| 通知對象 | 學員 | **家長**（上課提醒/作業/成果/到期） |
| 練習紀錄 | 學員自記 | **家長協助記 / 陪練打卡 / 小孩在家長手機上記** |
| 激勵迴路 | 對學員一人 | **雙迴路**：對小孩（貼紙/連續天數/遊戲化）＋ 對家長（看到錢花得值 → 續約） |
| 成果展示 | 學員自看 | **家長看 + 可一鍵分享給另一半/長輩**（轉介獲客更強） |

> 例外：**成人學生 / 青少年自學**（成人鋼琴、考音樂班的大孩子）仍是「本人即使用者」。所以家長層是**可選的代理關係**，不是寫死——帳號模型要能表達「這個學生由某家長代管」或「這個學生自己管」。

### 3.2 進步引擎完全不同：曲目精熟 ≠ 負荷漸進 ★ 最硬

健身版在 `studio-modalities.md` 把自己的引擎定義得很清楚：

> 引擎只懂「**可量化的負荷/量漸進**（組×次×負荷 → 漸進 → 體組成/肌力證據）」。靠**技術/段位**進步的項目（格鬥腰帶、藝術完成度）一律歸 **T3，明確排除**。

音樂的進步**正是那條被排除的技術/段位軸**：靠**曲目難度爬升 + 技巧精熟 + 檢定級數**，不是靠負荷量化。所以——

> **不能、也不該把音樂硬塞進健身引擎。** 必須自建一套**音樂原生引擎**。

**健身引擎 → 音樂引擎的物件抽換：**

| 健身引擎 | 音樂引擎（重做） |
|---------|----------------|
| Exercise 動作（主/次肌群 + 器材 + 組次負荷） | **Piece/Item 曲目·練習項**（曲目／音階／琶音／練習曲／視奏／樂理；屬性 = 調性/拍號/難度級/技巧標籤） |
| Program → Cycle → Day → Block（週分項 + 組間休息） | **Repertoire Plan 曲目計畫 → Assignment 每週指派**（本週練哪幾首、各練到什麼程度/速度） |
| WorkoutLog（每組重量×次數 + RIR/RPE） | **LessonNote 課堂紀錄**（老師：今天上了什麼、彈得如何、待改進）＋ **PracticeLog 練習紀錄**（家庭：哪天練了、練多久、練哪首） |
| BodyComposition（體脂↓肌肉↑ = 客觀成長） | **錄音/錄影 + 檢定/比賽/發表會**（同一首曲子第 1 個月 vs 第 6 個月的音檔對比、ABRSM/英皇/山葉/史坦巴哈級數、比賽名次、成果發表影片）= **音樂版的客觀成長硬證據** |
| 動作庫（free-exercise-db 873） | **曲目庫/教材庫**（分級曲目、教本進度、音階琶音表；可由老師自建或接分級大綱） |
| 器材庫 Equipment | **樂器/教材**（學生的琴、用的教本版本）— 較弱，非核心 |

**新增、健身沒有的音樂原生概念：**
- **節拍器目標速度（BPM）** — 「這首練到 ♩=120 算過關」是音樂最自然的可量化進步指標（這是音樂少數能量化的東西，要善用）。
- **錄音作為一級物件** — 練習錄音、課堂片段、成果影片。音檔/影片的「**前後對比**」是留存王牌（家長最愛）。
- **檢定/比賽行事曆** — 報名期、考試日、曲目要求；倒數與備考進度追蹤。
- **樂理/聽寫** 等非演奏練習項。

### 3.3 主戰場翻轉：「課與課之間」才是產品核心

| | 健身版 | 音樂版 |
|---|--------|--------|
| 價值發生地 | **付費課堂內**（Tier A 深記錄） | **每週課之間的家庭練習**（每天 15–30 分） |
| 課外的地位 | Tier B 生活習慣，次要、零摩擦、不要求完整 | **第一痛點、第一價值**：小孩不練、家長盯到累、老師下週才發現沒練 |
| 產品重心 | 課堂結構化記錄 | **家庭練習的指派 → 打卡 → 回饋閉環** |

→ **健身版裡的配角（課外追蹤），在音樂版升為主角。** 這條閉環是音樂版差異化的核心：
**老師課後口述指派**（Yo 解析成本週作業）→ **推到家長 LINE** → **小孩每天練習打卡/錄音**（家長協助）→ **老師上課前看到這週練況** → 下週調整。**這正是 AI 副駕語音輸入最該服務的車道。**

### 3.4 其他較小但要注意的差異
- **頻率更固定**：幾乎都是「每週固定時段」週課 → 排課更像**週期性循環排程**；**請假補課（make-up）**比健身更高頻、更敏感（家長很在意補不補得到）。
- **內容 per-樂器**：鋼琴≠小提琴≠吉他≠聲樂，如同健身的多專項。對策同健身——**通用包（老師自建曲目）Day 1 全覆蓋**，分級大綱（英皇/山葉…）做成可選的官方「Know-How 包」。
- **檢定生態是商機也是內容**：英皇 ABRSM、Trinity、山葉、河合、各地音樂班甄試——備考流程標準化，可做成模板（對應健身的「器材感知教案」）。
- **季節性**：成果發表會、檢定季、寒暑假（密集班）有明顯季節節奏，營運提醒要懂這個節奏。

## 5. 品牌適配：「有練」在音樂更名正言順

- 健身版命名邏輯：有練（有在健身）＋ 英文諧音「Yo, lean」。
- **音樂版**：「**有練**」直接 = 「**有練琴 / 有練習**」。`練` 字本身就是音樂教學的核心動詞（練琴）。**每個琴童家長每天的那句「今天有練琴嗎？」，就是這個產品的名字。**
- slogan「**有練，有差**」原封不動成立（有練琴，程度差很大）。英文「lean」的雙關在音樂用不上 → 音樂版**主打中文「有練（琴）」**，弱化 lean 梗即可。
- AI 副駕仍叫 **Yo**（諧「有」），但口吻轉向**對家長與小孩**（溫暖、鼓勵、給家長安心），不是健身的同溫層口吻。
- 命名建議：產品線名 **Yolian Music（有練 · 音樂）**；對外可獨立敘事，與健身版同源不同臉。

> 結論：品牌不但能搬，**搬到音樂反而更貼**。這降低了做獨立產品的命名成本。

## 6. 市場假設與既有類似工具（台灣 + 缺口）

**市場假設（待後續正式競品研究驗證）：**
- 台灣音樂教學長尾巨大：個人鋼琴/小提琴老師、社區琴行、音樂教室、才藝中心；數位化程度**比健身更低**，多數靠 LINE 群 + 紙本聯絡簿 + 老師記憶。
- 家長付費意願高、對「看得到進度/成果」極敏感（才藝是高焦慮消費）；**檢定與發表會**是天然的付費價值錨點。

**既有類似工具（prior art，國外為主）：**
- **My Music Staff / Opus1.io / Fons / Duet Partner** — 音樂教室「**行政管理**」（排課/收費/出缺勤），對標健身的 17FIT/SimpleTraining 那層。**強行政、弱練習閉環、無 AI、非在地（無 LINE）**。
- **Tonara / Modacity / MuseFlow** — 「**練習追蹤/陪練/遊戲化**」，對標成長/習慣那層。**強練習、弱營運**，且各自為政。
- **缺口（與健身版同形）**：**沒有人把「完整營運 OS + 家庭練習閉環 + AI 語音副駕 + 台灣 LINE 零安裝家長端」縫進同一個產品**。健身版發現的那個真空，在音樂同樣存在，且在地缺口更大。

> ⚠️ 範圍說明：本文是**適配評估**，competitor 名單為快速佐證、非完整競品研究。若決定推進，需補一輪音樂教學 SaaS 的正式競品研究（如健身版的 `competitor-research.md`）。

## 7. 風險與否決點（什麼會讓它不成立）

| 風險 | 說明 | 緩解 |
|------|------|------|
| **家長層拉高複雜度** | 帳號/權限/通知多一層代理關係 | 把「家長代管」做成可選關係，不影響成人自學情境 |
| **練習打卡的依從性** | 小孩/家長會不會真的天天打卡？ | 零摩擦（一鍵/語音/錄音）＋ 雙迴路激勵；老師端就算沒打卡也有課堂紀錄當底 |
| **音樂引擎要重做** | 不能複用健身引擎，是真成本 | 但 OS 層（最花工的營運模組）全沿用，重做的只是內容引擎；且通用包 Day 1 覆蓋 |
| **內容深度（分級曲目庫）** | 英皇/山葉等大綱要逐步建 | 同健身策略：通用自建包兜底，官方分級包由市場拉動 |
| **與健身版資源排擠** | 兩條產品線 | 共用 Action 層/OS，邊際成本主要在引擎+家長層；可序列推進，不必並行 |
| **檢定版權/商標** | ABRSM 等名稱使用 | 只做「備考流程/曲目追蹤」，不冒用官方認證；名稱使用走描述性 |

**真正的否決點**：若「家庭練習閉環」做不出依從性（小孩就是不練、家長就是不記），產品會退化成「又一個排課工具」——那塊正是與 My Music Staff 拉開差距的關鍵，**必須在 MVP 驗證**。

## 8. 結論與建議

1. **做，但做成獨立產品 Yolian Music**：獨立品牌敘事、獨立網頁、獨立部署（如你要求）。底層**共用 Action 層 + 通用教練 OS 模組**，**抽換訓練引擎為音樂引擎**，**疊一層家長代理帳號**。
2. **MVP 主攻一件事證明價值**：**「課後口述指派 → 家長 LINE → 家庭練習打卡/錄音 → 老師上課前看到」這條閉環**＋基本營運 OS（排課/堂數/消課/到期提醒）。這是與純行政工具拉開差距的命門。
3. **留存王牌＝錄音前後對比 + 檢定/發表成果**：把「客觀成長」從健身的 InBody，換成音樂的**音檔/影片對比與檢定級數**，餵 AI 成長敘事推給家長。
4. **品牌零成本紅利**：直接用「有練（琴）」「有練，有差」。
5. **分期**：先單一樂器（鋼琴，市場最大）跑通閉環 → 多樂器（通用包）→ 分級官方包/檢定生態 → 商業化閉環（金流/發表會售票等）。
6. **下一步**：完整系統設計見 `product-architecture.md`；推進前補一輪音樂教學 SaaS 正式競品研究。

> 一句話：**商業模式照搬，引擎重造，加一層家長。** 健身版「OS 與內容解耦」的紀律，這次得到回報——讓音樂版只需重做該重做的，其餘照用。
